## chunk 优化

不一定要“物理上拆成多个文件”，但一定要“逻辑上拆分并结构化”。

如果做的是 RAG，真正影响效果的通常不是“原始文件大”，而是这几件事：

1. 检索时是否按语义块切片，而不是整篇塞进去。
2. 每个 chunk 是否边界清晰，有明确主题。
3. chunk 是否带了足够 metadata，方便过滤和重排。
4. 是否保留章节层级，让模型知道“这段属于哪个系统、哪个工况、哪类操作”。

所以先给结论：

- 如果切片流程足够好，这种大文件可以不拆成多个物理文件。
- 如果这个文件内容跨度特别大，混合了很多系统、工况、操作步骤、报警处理、定值说明，那么拆成多个“主题文件”通常会更利于检索质量、维护和更新。

可以把这个问题分成两层看。

**一、对大模型来说，真正难的不是“大文件”，而是“混杂”**
大模型在 RAG 里一般不会直接理解整份大文件，而是理解被检索出来的 chunk。
所以问题不在于“文件 5 万字还是 20 万字”，而在于：

- 一个 chunk 里是不是只讲一件事
- 相邻 chunk 会不会把一个操作步骤切断
- 检索出来的内容是不是刚好落在正确章节
- 同一个问法会不会检出很多相似但不完全对应的段落

如果大文件里同时有：

- 启停操作
- 正常运行监视
- 异常处理
- 联锁保护
- 定值范围
- 设备结构说明

那它天然就是“多主题混合文档”。这种文档即使能切片，也容易出现“语义污染”：用户问 A，检索结果混进 B。

**二、是否拆文件，核心看目标不是看文件大小**
更建议依据“知识单元边界”决定，而不是依据“字数”决定。

适合拆分成多个文件的情况：

- 一个文件里覆盖多个大主题，彼此查询意图差别很大
- 后续更新是按章节/系统更新，不是整篇更新
- 希望给不同 chunk 打更明确的来源标签
- 需要权限控制、版本管理、责任人管理

不一定要拆的情况：

- 原文有很清晰的标题层级，`# / ## / ###` 很规范
- 切片器能按标题递归切分
- 能给每个 chunk 附带章节路径 metadata
- 有 rerank 或 parent-child retrieval，能补足上下文

所以，**大文件本身不是原罪，结构混乱才是。**

**建议的做法**
不是先急着把它拆文件，而是先做“结构化改造优先，物理拆分其次”。

优先做这几件事：

- 统一标题层级
  例如按“系统 -> 场景 -> 操作/规则 -> 步骤/参数”组织。
- 给每段内容明确主题名
  不要用模糊标题，比如“其他”“注意事项”“补充说明”。
- 把长段落拆成短的语义段
  一段尽量只表达一个规则或一个动作。
- 对步骤型内容保留完整步骤边界
  不要把“步骤 1-6”切成互相断开的 chunk。
- 给 chunk 保存 metadata
  比如：
  - `source_file`
  - `section_path`
  - `system=主机/汽机/锅炉/DEH...`
  - `scenario=启动/停机/正常运行/异常处理`
  - `content_type=步骤/限制值/说明/故障处理`
  - `device`
  - `version`
- 对表格和定值做专门处理
  这类内容很容易在普通切片里失真，最好单独转成“字段化文本”或结构化记录。
- 保留父级摘要
  每个大章节生成一个 summary chunk，配合细粒度 chunk 检索，效果通常更稳。

**如果要拆，建议按“查询意图”拆，不要按页数拆**
比如这种运行规程，通常比“平均切成 10 个文件”更好的方式是：

- 机组概述/适用范围
- 启动规程
- 停机规程
- 正常运行监视与调整
- 异常与事故处理
- 联锁保护与报警
- 运行参数与限制值
- 设备/系统说明

这样拆的好处是，检索时天然缩小语义范围。

**一个很关键的判断标准**
可以问自己一句：

“用户未来提问时，是否会天然落在某个明确主题下？”

如果答案是“会”，那按主题拆分通常有价值。
如果答案是“不会，很多问题都要跨章节拼接”，那就保留单文件，但一定要做层级化 chunk 和父子检索。

**关于‘大文件不利于大模型理解’这句话，精确一点说**
- 对“直接整篇喂给模型”来说，是的，不利于理解和定位。
- 对“RAG 检索后只喂相关 chunk”来说，不是文件大不大，而是切得好不好、检得准不准。

所以重点是：

- 怎么定义知识边界？
- 怎么切 chunk？
- 怎么加 metadata？
- 怎么让检索先找到对的章节，再找到对的段？

## RAG 调用侧的并发与性能优化点

之前说“平均两次 embedding + 五次 LLM，一次几千 token”。真正的性能瓶颈往往不是 vLLM 本身，而是把“长 prefill”重复做了 5 遍。下面这些改动通常比继续拧 vLLM 参数更有效。

1) 先从结构上把 5 次 LLM 压到 1~2 次

高并发时，最贵的是长输入 prefill。常见合并方式：

- 把“query 改写、检索指令生成、证据选择、最终回答（含引用格式）”尽量合成一次模型调用
- 或最多两次：一次生成检索 query/过滤条件；一次拿检索结果生成最终答案
    这样等价于把每轮对话的“几千 token prefill”从 5 次降到 1~2 次，吞吐和尾延迟通常是数量级改善。

2) 让 APC 真正命中：把“稳定前缀”做成强约束

APC 的前提是新请求与旧请求共享相同前缀 KV block。

因此在 RAG 侧要做到：

- 系统提示词、角色说明、输出格式、工具 schema：尽量固定不变
- 把高度动态的部分（用户问题、检索片段）放在 prompt 后半段
- 检索片段的拼接格式要稳定：同样的分隔符、同样的字段顺序、同样的引用模板
- 不要每次请求都随机插入时间戳、随机 trace id 到系统提示词里（这会破坏前缀一致性）


如果以后跑多副本：需要尽量把同前缀请求路由到同一副本，否则缓存命中会被稀释。Ray 的 prefix-aware routing 文档就是围绕这个问题设计的。

3) 控制“检索带来的 token 洪水”，优先减少 prefill

现在“每次几千 token”，通常来自：topK 太大、chunk 太长、重复 chunk、无效上下文。建议优先做：

- 检索：更激进的去重与聚合（同文档相邻 chunk 合并/裁剪）
- rerank：强制只保留 N 个证据（比如 6~12 个短 chunk，而不是 30 个长 chunk）
- 上下文压缩：对每个 chunk 做摘要/要点提取再送大模型（可用更小的模型或规则）
- 预算化：在拼 prompt 前做 token 预算器，硬性卡住“证据区最大 token”


这一步会同时让 vLLM 的 chunked prefill 更有效（长 prompt 变少）、APC 更容易命中（固定前缀占比更高）。

4) 并发策略：RAG 编排层做“背压 + 批处理”

- embedding：把多用户同时到来的 query 合并 batch（embedding 模型吞吐会更好）
- 向量库：异步 IO + 连接池 + 超时；对热门 query 做短 TTL 缓存
- LLM：应用层做并发上限与排队，不要无限并发把 vLLM 推到 preemption/recompute（文档已经说明这会伤端到端延迟）。 

5) 用指标把瓶颈定性，否则容易“盲调”

建议把每轮对话拆成四段打点：

- embedding1/2：耗时、批大小
- retrieval：topK、返回 token 数
- LLM：TTFT、TPOT、输入/输出 token
    然后对照 vLLM 的 /metrics 里的 KV 使用率、prefix cache 命中率、请求延迟直方图一起看，vLLM 官方指标设计文档就按这种可观测性思路写的。 

一个“优先级路线图”

1. vLLM：>=0.10.2 + 开 APC + 开 chunked prefill + 先把 preemption 打掉（靠 gpu_memory_utilization / max_num_seqs / max_num_batched_tokens）。 
2. RAG：把 5 次 LLM 压到 1~2 次；同时做 prompt 预算与证据裁剪，让“几千 token”下降。
3. 监控：上 Prometheus/Grafana，盯 KV 使用与 prefix cache 命中，形成可重复的压测-调参闭环。 
4. 仍然被长 prompt 干扰：再考虑 vLLM 的 Prefill/Decode 解耦（experimental）。
